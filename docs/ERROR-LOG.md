## API-001：仓库目标理解过宽（2026-09-08）

- 现象：最初把“上传项目”理解为将协作归档加入现有 `Kitjesen/motor`。用户明确要求另建 API 仓库。
- 原因：把硬件工程和 API 工具的仓库边界混在一起。
- 修正：另建私有 `Kitjesen/easyeda-api`，收录 API 代码、桥接补丁、安装配置和研究资料。未向 motor 提交或推送内容。
- 验证：以新仓库远端、隐私属性、提交 SHA 和文件目录作为交付证据；结果另见仓库提交与交付说明。
- 后续规则：明确当前对象是硬件设计还是 API 工具；研究材料中的仓库名和命令应随目标修正。

## API-002：文档与源码缓存绑定（2026-09-08）

- 现象：原文档检查强制要求所有下载的第三方源码缓存存在；迁移轻量仓库后会报缺文件。
- 原因：没有区分版本/来源索引校验与完整缓存物化校验。
- 修正：默认校验 40 项来源、提交、路径及文档链接，明确报告未物化数量；`--require-cache` 才严格要求下载文本存在。保留固定提交下载命令。
- 验证要求：默认检查通过；没有缓存时严格检查必须失败，不能报告已验证源文本。

## API-003：迁移脚本的 Windows 路径字面量错误（2026-09-08）

- 现象：临时 Python 打包脚本使用以反斜杠结尾的 raw string，解析时报 SyntaxError。
- 影响：在执行前即失败，没有写入文件或操作编辑器。
- 修正：用 Path 转换及显式路径分隔符拼接，重新运行成功。
- 后续规则：Windows 路径不使用末尾单反斜杠的 raw string；仓库内命令采用相对路径，文件生成后做语法和内容检查。

## API-004：Git 把补丁的空白上下文行当成尾随空格（2026-09-08）

- 现象：首次提交前 `git diff --cached --check` 报 bridge-local-v2.patch 中的单空格行，提交流程停止，尚未创建远端。
- 原因：统一 diff 用一个空格表示空白上下文行，按普通代码文本检查会报尾随空格。
- 修正：只对 `.patch` 文件设置 `whitespace=-blank-at-eol`；保留补丁内容、哈希及应用语义，其他源文件继续检查。
- 验证要求：Git 提交差异检查通过，补丁哈希与已验证安装一致。禁止通过全文件 trim 破坏补丁格式。

## API-005：资料收录偏重 MCP，PCB 工程依据不足（2026-09-08）

- 现象：原有 F01–F05 主要记录 PCB 操作接口，缺少完整的板级布局依据；漏掉了官方器件分组、规则生成、PADEN 和制造层可视化等直接相关项目。
- 原因：以 MCP 仓库关键词发现为主，没有沿官方扩展、器件厂商、制造要求和真实机器人硬件分别检查。
- 修正：增加 PCB 专题、23 项精选来源、设计指导与 topics 检索；补录 11 个上游仓库，使版本索引由 19 个增至 30 个。明确默认值、功率密度、参考板修订等适用边界。
- 验证：检查固定 SHA/路径、文档链接、来源状态和主题检索；未宣称已运行社区规则或分析现场 PCB。
- 后续规则：资料发现按任务需要分层；收录状态与已接入状态分开，功能名称和工具数不替代工程依据。

## API-006：手动更新命令未覆盖后来加入的仓库（2026-09-08）

- 现象：更新脚本默认只检查硬编码种子，后来通过参数加入的新 PCB 仓库会留在旧版本。
- 原因：合并保存了新条目，默认查询集合却没有合并现有目录。
- 修正：未传参数时使用种子与现有条目仓库名的去重并集；显式传参数时仍只更新所选仓库。
- 验证要求：检查默认集合包含全部 30 个条目、显式选择仍保持原行为；本轮未额外刷新无变化的其余仓库。

## API-007：README 下载超时掩盖已成功读取的版本信息（2026-09-08）

- 现象：新增两个 iBOM 仓库时，GitHub 元数据已读到，raw README 下载超时；查询目录将整项写成 error，专题生成器因此拒绝未验证路径 O09。
- 原因：可选说明文件下载和必要版本/文件树查询共用整个条目的异常处理。
- 修正：README/包文件下载失败单独记录 referenceFetchWarnings，保留已经取得的版本和文件树。专题按固定提交读取文本时支持 GitHub Contents API 备用路径。
- 验证要求：两条目录有真实 SHA/文件树，专题无缺源；保留异常字段而非把下载失败误报成成功。此故障未操作编辑器。

## API-008：按记忆拼文档号导致引用对象错误（2026-09-08）

- 类型：本轮调研中实际发生；未操作编辑器。
- 现象：查找电机布局资料时尝试 SLVAEJ2，打开后实际标题为 TPS55165-Q1 Layout Guideline，与拟查的电机系统资料不符；另有猜测 PDF 路径未能读取。
- 原因：把记忆中的文档号当成已核实来源；链接可打开也不能证明主题正确。
- 修正：弃用不相关引用；从 TI 产品页正式链接定位热参数、瞬态热阻和 SOA 文档，核对标题、编号、修订及相关章节后写入 Skill 来源表。
- 验证：SOA 正式文档为 SLUAAO2，瞬态热阻为 SLUAAT8，热参数为 SPRA953D；Skill 没有收录 SLVAEJ2 或未经确认的替代编号。
- 后续规则：先确认来源身份再提炼结论；读取失败不等于文档不存在，目录已读与正文已读分别记录。

## API-009：PCB 指导文档缺少独立 Skill 入口（2026-09-08）

- 类型：仓库结构检查确认的交付缺口。
- 现象：用户查找“电机功率级布局 Skill”时，现有内容是 PCB-DESIGN-GUIDE.md 与来源目录，没有对应 SKILL.md。
- 原因：资料收录、指导文档和可发现的 Skill 未分别落实，专题深度也不足以直接支撑逐项布局审查。
- 修正：新建 motor-power-stage-layout 入口及 9 份参考文件；补上具体回路/焊盘检查、模型边界、故障行为与验收场景；本机使用目录联接指向仓库同一份源文件。
- 验证要求：Skill 结构、全部本地引用和 YAML 有效，联接与仓库内容一致，仓库必要检查通过；不把这些结果当作真实 PCB 或自动布局能力验证。
- 后续规则：对“是否已收录/安装/适配/现场验证”分别回答，并提供真实路径。

## API-010：Skill 校验运行时缺少 YAML 依赖（2026-09-08）

- 类型：本轮本地校验实际发生；与编辑器无关。
- 现象：首次调用官方 quick_validate.py 时，所选捆绑 Python 报 ModuleNotFoundError: yaml，尚未进入 Skill 格式检查。
- 原因：误以为该 Python 环境已包含验证器所需 PyYAML。
- 修正：检查现有解释器，改用已安装 PyYAML 6.0.3 的 miniconda3 Python；未安装新依赖，也未改变全局环境。
- 验证：官方校验器返回 Skill is valid；额外检查 9 份参考、11 个本地引用、界面 YAML 和 9 项算例结果，均通过。
- 后续规则：校验器依赖缺失与被校验内容错误分别报告，优先使用已有可用运行时。

## API-011：安装入口的组合命令被策略拒绝（2026-09-08）

- 类型：本轮工具实际拒绝；命令未执行。
- 现象：将目录联接、哈希校验和非必要空目录清理放在同一 shell 请求中，自动审批返回 blocked by policy，未提供更细的触发原因。
- 修正：省去非必要清理，先只读确认源目录和目标不存在，再单独创建新目录联接；没有覆盖已有内容。
- 验证：单独创建命令成功，返回 Junction 及正确源目录；后续逐文件验证内容一致。
- 后续规则：安装与清理不混在同一请求；被拒命令不能当作已执行，也不猜测具体拦截原因。

## API-012：局部避让不能替代整页排版（2026-09-10）

- 类型：现场原理图与原生 PDF 实际复查。
- 现象：逐个移动标签后，仍有去耦电容位号压线、相邻数值重叠、模块标题位置不一、大片留白与局部拥挤并存。
- 修正：先统一模块框架、标题和空间分配，再完整移动功能块，最后按原生 PDF 修饰位号与数值；双接口按相同方向和相对偏移展示。
- 后续规则：按整页与局部两个尺度验收，不能仅据“不重叠”判定标签位置合适。详见[原理图注意事项](SCHEMATIC-EDITING-NOTES.md)。

## API-013：显示字段规范化导致完整对象核验误报（2026-09-10）

- 类型：现场写入后的独立回读确认。
- 现象：文字和布局已写入，但严格对象比较因部分 `fillColor: null` 变成 `#000000` 而失败。
- 原因：该客户端在部分文字颜色从空值改为黑色时补齐显示字段；颜色原本已是黑色的对象不一定发生同样变化。
- 修正与验证：逐字段检查实际差异，仅修正已观察到的显示规范化预期，另行回读通过；没有重放成功写入，也没有放宽电气身份和连接检查。

## API-014：新增文字、窗口状态与枚举值分别处理（2026-09-10）

- 类型：现场 API 失败及恢复观察。
- 现象：源码批次追加多个文字曾被拒；正式文字创建时传字符串对齐名称也未成功。另有后台状态下写入失败、恢复目标窗口后同一计划成功的情况。
- 修正：已有记录修改与新增非电气图元分开，新增使用正式 API；核对本版枚举定义，`LEFT_TOP` 对应数值 `1`。每次失败先读现有对象，确认是否部分创建后才决定下一步。
- 边界：不能证明每次 `Source rejected` 都由同一原因造成，不能据拒绝次数推断缺少许可。工具报告用户 Esc 中断时停止本轮，不继续后台修改。

## API-015：历史记录与写入前基线混用会产生错误归因（2026-09-10）

- 类型：现场网络核查与离线导出解析发现。
- 现象：忽略 EPRU 空 body 删除记录会重新计入旧对象；仅用任务最初快照比较后续状态，会把实际写入前已出现的变化归到当前脚本。
- 修正：按文档分隔，以对象 ID 为状态表键，按文件出现顺序重放更新与删除；分别保留任务开始、紧邻写入前、写入后三个状态。网络标签更换父级还需检查是否新建了绑定属性却留下旧悬空标签。
- 验证：本次重排后独立检查的 207 件、557 个引脚端点、125 个连接分区和 63 个命名网络保持一致；这些数量仅是本次观测，不硬编码为通用验收条件。

## API-016：最后微调后的导出仍须独立完成（2026-09-10）

- 类型：现场最终导出超时与用户中断。
- 现象：中间整体排版 PDF 已成功导出；最后几处文字微调保存后，新 PDF 导出超时，随后电脑操作工具报告用户按 Esc 中断。
- 处置：保留已保存的修改与独立回读结果，明确最后版本的 PDF、完整工程导出尚未完成；不拿中间 PDF 当作最新图面证据。
- 后续规则：导出结果关联本次调用及新文件，确认请求成功再后处理。本文和 Skill 的文档更新不操作现场电路，也不补充宣称未完成的导出或实板验证已经通过。

## API-017：通用 Skill 校验器与官方元数据字段不匹配（2026-09-10）

- 类型：本次文档同步后的本地校验实际发生；未操作编辑器。
- 现象：`quick_validate.py` 拒绝官方 Skill 原有的顶层 `compatibility` 字段，其允许字段列表不含该项。本次只追加参考入口，没有修改官方 frontmatter。
- 处置：保留原有元数据，记录该校验未通过的原因；另行解析 YAML、检查参考入口和文件哈希，不把这些检查冒充通用校验器通过。
- 验证：仓库 11 项测试与两组文档检查通过；从固定官方提交进行临时目录隔离安装（跳过依赖安装、不启动 Bridge），生成的参考文件与仓库源文件逐字一致，Skill 入口存在。本机已安装副本也已同步并核对哈希。

## API-018：运行 session 与重建的窗口不能沿用旧假设（2026-09-10）

- 类型：现场恢复中实际发生，提炼自 E192/E193/E201。
- 现象：读取尚未退出就生成依赖计划，因输出不存在失败；恢复后 Bridge 窗口 ID 已改变，active 又指向参考工程。
- 修正与验证：等待真实进程退出；重新枚举并逐窗口读取项目/图页身份，只更新确认属于同一目标的明确窗口 ID。守卫拒绝后没有落到参考工程，也没有重放另一页已完成的修改。
- 后续规则：运行 session 不是完成标记；active、旧窗口 ID 和历史文件均不是目标身份的充分证据。已创建但未接线必须如实报告。

## API-019：阶段失败不能否定之前已经写入的对象（2026-09-10）

- 类型：现场 API 返回与独立回读确认，提炼自 E195。
- 现象：修改旧说明已保存，后续新 TEXT 创建返回 `undefined`，整阶段报失败。
- 修正与验证：独立回读列出已修改与尚不存在的对象，仅补缺失说明并检查唯一性，没有整批重放。
- 后续规则：按对象判定实际状态；正式创建 API 也不能以方法名或一次历史成功代替本次回读。与 API-014 的早期成功案例并列保留，不推广为必然成功的替代路径。

## API-020：追加源码改变了末条记录的分隔语义（2026-09-10）

- 类型：离线脚本解析失败及现场源码拒绝，提炼自 E196/E200。
- 现象：生成文本中转义错误将实际换行放进字符串；修复后又因原末条无末尾竖线、追加后成为中间条而被拒。
- 修正与验证：用实际异步执行包裹方式做语法解析；补齐新中间条的分隔符，保持合法末条格式；独立回读确认失败时的实际状态后才应用修正版。
- 后续规则：CommonJS 的顶层 `await` 报错不能代替 `AsyncFunction` 上下文检查；PowerShell 显式检查前步退出码，失败不进入后续应用。源码精确守卫继续保留。

## API-021：同颜色、同封装的 LED 也不能按记忆换件（2026-09-10）

- 类型：真实库查询和暂存引脚回读确认，提炼自 E199。
- 现象：记忆中预计的低 Vf 0603 绿色采购号实际对应 0805 器件，另一候选为高 Vf 且库中标停产；最终两颗真实 0603 LED 的阳阴脚号又相反。
- 修正与验证：错误候选未落入最终电路；按实际查询核对 MPN、封装、供应状态和准确原厂资料，暂存后读引脚再接线，分别验证极性、网表和采购绑定。
- 后续规则：颜色是光学要求，不是电气规格。限流和 GPIO 驱动按实际 Vf/电平余量审查，亮度、电流与复位行为仍留实测；不能只改 Value 或旧模型颜色。

## API-022：云库 UUID 与项目内库 UUID 不是同一身份层（2026-09-10）

- 类型：现场真实器件导入后的存档核验确认。
- 现象：项目内 Device/Symbol/Footprint UUID 与查询到的云端 UUID 不相等，若直接要求字面相等会误报采购绑定错误。
- 修正与验证：同时保留真实库查询、项目 DEVICE 来源关系、符号/封装引用、采购属性及引脚极性证据，核对完整来源链。
- 后续规则：只按手填料号不能证明真实绑定；合法导入分配新 UUID 也不能直接判错。原样工程没有独立内嵌网表时，分别报告实时网表和存档有效实体，不宣称读取了内嵌网表。

## API-023：NC 属性变化不等于原生十字移动（2026-09-10）

- 类型：现场 PDF 局部检查与逐像素比较确认，提炼自 E198/E203。
- 现象：正式 NC 十字轻微接近或碰到脚号。坐标属性修改后回读通过，实际 PDF 十字没有移动。
- 修正与边界：恢复无效偏移，保留正式电气 NC；本版尚未确认受支持的实例级号码/十字位置覆盖，不改共享符号、不用普通画线或涂白假装解决。
- 后续规则：新 NC、长网名和脚注也纳入局部放大。只移动必要文字使位号/型号近邻成组、网名避开发光箭头；图面缺口与电气核验分别记录。

## API-024：渲染失败要先区分文件新鲜度、路径与运行时（2026-09-10）

- 类型：本地导出后处理实际发生，提炼自 E197/E202；没有因此改动现场电路。
- 现象：复用按脚本目录定位的渲染程序，实际读取了旧轮次 PDF；另一次辅助脚本名 `inspect.py` 遮蔽 Python 标准库，使 PDF 库无法导入。

## API-028：3.3V 状态灯由红换蓝需要重新做压降预算（2026-09-10）

- 选型依据：本次真实库选择 LITEON LTST-C193TBKT-5A / C125103。原厂资料在 25°C、5mA 下给出 Vf 最小/典型/最大为 2.65/2.80/3.05V，光强为 11.2/15/45mcd；后缀及测试条件属于器件身份的一部分。[原厂数据手册第 4 页](https://media.digikey.com/pdf/Data%20Sheets/Lite-On%20PDFs/LTST-C193TBKT-5A.pdf)、[采购身份](https://www.lcsc.com/product-detail/C125103.html)

- 后续规则：颜色、完整型号、真实引脚、压降预算逐层核对；最终亮度、电流、供电/温度边界与复位表现记入实测文档。保留电气核验、PCB ECO 和样机结果的独立状态。
